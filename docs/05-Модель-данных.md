# 05. Предварительная модель данных

Версия 0.1. Имена объектов — проектные. Итоговые метаданные утверждаются после Q. Это описание данных, без кода и конфигурации.

## Типы и общие правила

С(N) — Строка длиной N; Текст — Строка неограниченной длины; Ч(P,S) — Число разрядностью P с S дробными знаками; Д — Дата с временем; День — Дата без времени; Б — Булево; УИД — УникальныйИдентификатор; Спр.X/Док.X — ссылка на объект; Пер.X — перечисление. После поля «!» означает обязательно для действующего элемента/принятия/проведения; «?» — необязательно; «условно» сопровождается правилом. Все количественные ресурсы — Ч(15,3), часы — Ч(10,3), деньги — Ч(15,2), цены/ставки — Ч(15,4), минуты норм — Ч(10,0).

Стандартные реквизиты справочника: Код С(20), Наименование С(150), ПометкаУдаления Б; прикладной Активен Б! (по умолчанию Истина). Стандартные реквизиты документов: Номер С(20), Дата Д!, Ссылка; для проводимых — Проведен Б. Во всех документах: Автор Спр.Пользователи!, Комментарий Текст?, Версия Ч(10,0)!, ИдентификаторОперации УИД!; время события фиксируется сервером. Снимки адреса/цены/политики не заменяются при изменении справочника.

Обязательность проверяется сервером, а не только формой. Ссылки на помеченные/неактивные объекты запрещены для новых операций; исторические ссылки сохраняются. Физическое удаление объекта при ссылках запрещено. Временно неизвестные данные — пустое значение с явной причиной, не фиктивный элемент «прочее» во всех справочниках.

## Перечисления и настройки

Перечисления вместо редактируемых справочников: Приоритеты (Критический, Высокий, Обычный, Низкий); СтатусыЗаявок (Черновик, Новая, Назначена, ВРаботе, Ожидание, Выполнена, Закрыта, Отменена); СтатусыЗаданий (Плановое, ВРаботе, Завершено, Отменено); СостоянияОборудования (ВЭксплуатации, Приостановлено, Выведено); ВидыМестХранения (Склад, Инженер); ВидыРабот (Диагностика, Ремонт, ТО); ВидыКлиента (ЮрЛицо, ИП, ФизЛицо); ВидыДоговоров (Разовый, Обслуживание); КаналыОбращения (Телефон, Email, Лично, Другое); ВидыЦелейSLA (Реакция, Решение); РежимыSLA (Календарный, Рабочий); ПолитикиТО (ОтПлана, ОтФакта); СтатусыПотребностейТО (Открыта, ЗаявкаСоздана, Выполнена, ТребуетРешения, Пропущена); РезультатыРабот (Устранено, НеисправностьНеВыявлена, РаботыПрекращены); ВидыПрямыхЗатрат (Проезд, Подряд, Прочее).

Состав статусов и приоритетов фиксирован, поскольку определяет алгоритмы переходов и SLA. Добавление свободного справочника статусов сделало бы эти правила неопределёнными. Редактируемые названия для интерфейса при необходимости не меняют идентификаторы.

Настройки: валюта С(3)!; календарь компании Спр.Календари!; горизонты назначения/ТО Ч(10,0)!; окно повторов Ч(10,0)!; лимиты вложений. В первом релизе одной валюты достаточно, справочники организаций и валют не создаются без Q-01.

| АктВыполненныхРабот | ПродажиПоЗаявкам оборот; РасчётыСКлиентами приход долга | Закрытие, подпись, уникальность исходных строк, точность суммы, согласованные цены |
| ОплатаКлиента | РасчётыСКлиентами расход долга | Клиент и акты совпадают, достаточный долг, равенство распределений |

Отмена и перепроведение заменяют наборы движений данного регистратора, а не добавляют вторую копию. До снятия проведения проверяются зависимости: акт→оплата, выполнение→списание/акт/закрытие, диагностика→выполнение, задание→фактические документы, план→созданные потребности. Регистры истории и аудит не стираются при отмене, записывается событие отмены.

Распределение труда: общий труд выполнения распределяется по весам норматив×количество работ; если сумма весов=0 — поровну между строками; округлить часы до 0,001, стоимость до 0,01, остаток добавить последней строке по стабильному ИД. При нуле строк труд хранится одной записью с пустой услугой и признаком «Без работы» в реквизите; в отчётах выделяется отдельно. Это проектное правило Q-12, предотвращающее удвоение часов при нескольких работах.

«ЗагрузкаИнженеров» не создаётся регистром накопления: интервалы, пересечения и свободные окна требуют регистра сведений, а не суммирования часов. «ЗапчастиУИнженеров» реализуется отбором единого Запасы по виду места, «ВыручкаПоУслугам» — отбором ПродажиПоЗаявкам. Такая модель сокращает дублирование.

## Основные связи и источники истины

- Клиент 1:N площадки, оборудование, контакты, договоры, заявки. Заявка N:1 оборудование; заявка 1:N задания, диагностики, выполнения, согласования, акты.
- Задание N:1 инженер и заявка; задание 1:N диагностические/фактические документы. В MVP одновременно активное задание по заявке только одно.
- Выполнение 1:N списания; строка выполнения 0:1 строка проведённого акта. Акт 1:N распределения оплаты.
- Оборудование 0:1 активный ПланТО; план 1:N потребности; потребность 0:1 активная заявка, историю заменённых заявок восстанавливают по событиям заявки и аудиту потребности.
- Остаток/стоимость — Запасы; фактический расход — ИспользованиеЗапчастей; выручка — ПродажиПоЗаявкам; долг — РасчётыСКлиентами; статус — ЗаявкаКлиента+неизменяемая история; история не служит второй редактируемой карточкой.
- СледующееТО рассчитывается из плана, потребностей и ВыполнениеТО; даты в форме оборудования — вычисляемые. Нельзя вручную исправить дату последнего ТО без подтверждённого факта.

Требуемые индексы/разрезы доступа: заявки по статусу/приоритету/принятию; задания по инженеру/плановому началу; запас по месту/детали; занятость по инженеру/началу; потребности по плану/дате; контроль SLA по текущему сроку/состоянию. Конкретные индексы метаданных проверяются планом запроса на выбранном релизе платформы.
