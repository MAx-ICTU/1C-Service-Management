## Фиксация каждого этапа

1. Документация/задача с ID, границами/проверками/неопределённостями.
2. Ветка stage/NN-name от main; один этап может иметь несколько исправляющих коммитов.
3. Diff и протокол с platform/version, commit, действиями/результатами.
4. Push в выбранный origin, PR с описанием/ограничениями.
5. Приёмка/merge, неизменяемый тег завершённого этапа.
6. Обновление 12 и ссылки на commit/PR/tag; отложенные тесты не помечать пройденными.

Для документации текущего этапа допустим отдельный тег docs-v0.2-review: он означает версию на ревью, не утверждение. В существующий непустой GitHub-репозиторий не выполнять force-push и не перезаписывать историю: сначала читать default branch/состав, переносить материалы через отдельную ветку и PR. Для нового пустого репозитория отправить сохранённую последовательность v0.1→v0.2 после выбора владельца/имени/видимости.

## Шаблон протокола этапа

Автор текущих технических коммитов Codex <codex@local.invalid> выбран явно при отсутствии пользовательской Git-идентичности. Будущие коммиты могут использовать согласованные имя/email пользователя без переписывания прошлых.

## Актуализация документации после приёмки этапа

README — внешняя презентация продукта для руководителей, технических специалистов и потенциальных работодателей. PROJECT-STATE.md — внутренний контекст разработки. Технические протоколы — доказательства выполненных работ и проверок. Не смешивать эти назначения.

После приёмки каждого этапа необходимо:

1. Обновить статус соответствующего этапа в главном README. Использовать «Завершено», «В работе» и «Запланировано». «Завершено» допустимо только после подтверждённых проверок и приёмки; один коммит не является основанием.
2. Обновить PROJECT-STATE.md: текущий этап и статус, решения, действия, ограничения, следующий разрешённый шаг и ссылки.
3. Указать в README фактически реализованные возможности; отделить их от планов R1 и перспектив после R1.
4. Добавить появившиеся реальные демонстрационные материалы. Пока интерфейс не реализован, не публиковать фиктивные скриншоты и не обозначать ожидаемые сценарии как готовые.
5. Сохранить технические детали, результаты проверок и ограничения в протоколах. Исторические данные не удалять; при этом существенные ограничения функциональности и среды должны оставаться видимыми в README.

Ошибки инструментов, пути локальных баз, служебные команды, хэши, UUID и внутренние обсуждения не выносить в главный README. Презентационное изменение документации не означает приёмку этапа, выпуск релиза или разрешение начать следующий этап.
