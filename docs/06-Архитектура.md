# 06. Предварительная архитектура

Версия 0.1. Выбор конкретного релиза платформы, СУБД, ОС и использования БСП — Q-14/Q-17.

## Развёртывание

Рекомендуется самостоятельная управляемая конфигурация на 1С:Предприятие 8.3. Основной клиент — тонкий. Промышленный вариант: клиент → кластер серверов 1С → согласованная поддерживаемая СУБД. PostgreSQL рассматривается как кандидат, точная версия проверяется по матрице выбранного релиза платформы. Для веб-клиента и будущих HTTP-сервисов добавляется веб-сервер с HTTPS. Клиенты не имеют прямого доступа к СУБД. Возможность такого разделения подтверждается [описанием клиент-серверного варианта 1С](https://v8.1c.ru/platforma/klient-servernyy-variant-raboty/); выбор топологии — решение проекта.

Учебный файловый стенд допустим, но целевая проверка транзакций, конкуренции и автономной работы регламентных заданий выполняется в клиент-серверном варианте. Расписания сервиса продолжают работать при закрытых пользовательских клиентах.

## Подсистемы

КлиентыИОборудование; СервисныеЗаявки; ПланированиеВыездов; ВыполнениеСервиса; Склад; ТО; SLA; ПродажиИРасчёты; Отчёты; Администрирование. АРМ — управляемая обработка, отчёты — СКД. Объекты платформы «Бизнес-процесс» и «Задача» в MVP не требуются: явного состояния заявки и заданий достаточно. Систему согласования с маршрутом можно добавить позже при реальной потребности.

## Клиент и сервер

| На клиенте | На сервере |
|---|---|
| Открытие форм, выделение, фильтры, подсказки, подтверждение пользовательского действия | Чтение/изменение ИБ, запросы, права и ограничения данных |
| Представление сроков и ошибок, навигация, ввод файлов | Расчёт SLA/ТО, подбор кандидатов, проверка календаря, стоимости и остатков |
| Предварительная проверка незаполненных полей для удобства | Полная повторная проверка обязательности и бизнес-инвариантов |
| Отправка компактной команды с ссылкой, версией и параметрами | Транзакция, блокировки, проведение, история и аудит |
| Запрос статуса долгого отчёта/задания | Регламентные и фоновые операции, будущие внешние вызовы |

Клиентский расчёт суммы не является основанием движения. Сервер получает выбранные строки, самостоятельно читает разрешённую цену, проверяет количество и согласование. Подбор инженера не удерживает транзакцию; подтверждение проверяется заново. Отчёт формируется по запросам с правами, а не выгрузкой всей базы на клиент.

## Общие модули и контракты будущей реализации

| Проектный модуль | Контракт без кода | Контекст |
|---|---|---|
| ЗаявкиСервис | Принять, сменить статус, зарегистрировать реакцию, проверить закрытие; ссылка+версия+команда → результат/список нарушенных правил | Сервер; вызов клиентом через узкую оболочку формы |
| ПланированиеСервис | Предложить кандидатов; подтвердить/перепланировать задание | Сервер |
| СкладСервис | Оценить расход, проверить остаток, сформировать движения регистратора | Сервер, внутри транзакции проведения |
| SLAСервис | Выбрать версию, рассчитать бюджет/сроки, зарегистрировать факт/паузу, зафиксировать нарушение | Сервер |
| ТОСервис | Выбрать потребности, создать заявку идемпотентно, подтвердить выполнение | Сервер |
| ЦенообразованиеСервис | Получить цены/ставки, проверить согласование и округлить строку | Сервер |
| РасчётыСервис | Проверить включение строк в акт, распределить платёж, проверить долг | Сервер |
| ДоступСервис | Проверить полномочия и доступ к объекту с учётом пользователя | Сервер |
| АудитСервис | Записать событие без секретов и персональных данных сверх нужного | Сервер |
| ПредставлениеКлиент | Сообщения, навигация, работа с управляемой формой | Клиент |

Не создавать один универсальный общий модуль со всеми функциями. Серверные модули без необходимости не публикуются для прямого клиентского вызова. Проверка прав выполняется в точке команды и в критических обработчиках записи/проведения; фоновые задания используют служебную роль. Привилегированный режим не является универсальным способом обхода ошибок доступа.

## Транзакции и конкурентность

Команда получает ожидаемую Версию. После блокировки объекта сравнивает её с актуальной; при несовпадении возвращает конфликт и предлагает обновить форму. Успешное изменение увеличивает версию. Один ИдентификаторОперации повторно не создаёт перехода/движения; результат повторной команды восстанавливается из истории/аудита. Для внешних команд позднее будет отдельный журнал идемпотентности.

Склад: блокировки пар место+деталь в стабильном порядке; назначения: инженер и затронутые даты, затем проверка пересечения; ТО: ключ план+плановая дата; акты: исходные строки выполнения; платежи: клиент+акт. Проверка вне транзакции предварительная, внутри — окончательная. Вызовы внешних сервисов и работа с интерфейсом внутри транзакции запрещены архитектурным правилом проекта.

## Регламентные задания

| Задание | Расписание — предложение | Идемпотентность / результат |
|---|---|---|
| КонтрольSLA | Каждые 5 минут | Уникальность заявка+цель; отметка успешного запуска и ошибок |
| ФормированиеПотребностейТО | Каждый день 06:00 | Ключ план+дата; транзакция на одну потребность, повтор после сбоя |
| ПроверкаПокрытияКалендарей | Ежедневно 05:30 | Уведомление администратору, если горизонт <400 дней; автоматические праздники не придумываются |
| КонтрольМинимальныхОстатков | Ежедневно 07:00 | Обновляемая очередь дефицитов/отчёт, не закупка и не движение |

Используется механизм регламентных/фоновых заданий платформы; повторный запуск дополнительно защищается прикладными ключами. Это опирается на [официальное описание механизма заданий](https://v8.1c.ru/platforma/mehanizm-zadaniy/). Резервное копирование выполняется средствами администрирования СУБД, не прикладным регламентным заданием проведения документов.

## Права и ограничение данных

Права платформы задаются ролями, а доступ инженера к строкам — ограничениями доступа к данным плюс проверкой команд. Возможности ограничений описаны в [системе прав доступа 1С](https://v8.1c.ru/platforma/sistema-prav-dostupa/). Конкретная матрица — проектное решение:

| Объект/операция | Диспетчер | Инженер | Кладовщик | Менеджер | Руководитель | Админ |
|---|---|---|---|---|---|---|
| Клиент, площадка, оборудование | Чтение | Связанные с заданиями, чтение | Минимум для выдачи | Изменение | Чтение | Полный |
| Заявки/переходы | Изменение | Связанные, чтение/факты | Связанные, чтение расхода | Чтение/согласование | Чтение | Полный |
| Задания/назначения | Изменение | Собственные, старт/завершение | Чтение для выдачи | Чтение | Чтение | Полный |
| Диагностики/выполнения | Чтение | Собственные, изменение до зависимостей | Расход, чтение | Чтение | Чтение | Полный |
| Складские документы | Чтение количества | Свой остаток, чтение | Изменение/проведение | Чтение количества | Чтение | Полный |
| Цены/акты/оплаты | Только согласованная стоимость заявки | Состав работ, без ставки/маржи | Без коммерческих цен | Изменение/проведение | Чтение | Полный |
| Себестоимость/ставки/прибыль | Нет | Нет | Себестоимость запасов | Предлагается чтение маржи | Чтение/настройка ставок через отдельное право | Полный |
| Политики/календари/аудит | Чтение сроков | Сроки своих заданий | Нет | Чтение политики договора | Чтение аудита | Изменение настройки/чтение аудита |

Трудовая ставка не доступна инженеру даже если сохранена в документе его выполнения: отдельные права на поля/доступную проекцию формы и серверные запросы. Полные наборы данных отчётов не отдаются клиенту, чтобы скрытое поле не стало способом утечки. После переназначения инженер сохраняет чтение собственных выполненных документов, но не новых заданий другого инженера; эту историческую политику требуется подтвердить Q-10.

## Будущие интеграции: только проект

REST API целесообразно строить на HTTP-сервисах с собственными командами предметной области, а не давать внешнему клиенту прямую запись регистров. Платформа поддерживает [HTTP-сервисы](https://v8.1c.ru/platforma/http-servisy/) и отдельный [автоматический REST-интерфейс](https://v8.1c.ru/platforma/rest-interfeys/); выбор командного API — рекомендация проекта. В текущем этапе не создаются сервисы, эндпоинты и интеграционные метаданные.

Контракт будущего API: версия v1, внешние UUID, серверное время, версия объекта, идентификатор операции/корреляции; команды принятия, назначения и выполнения вызывают те же серверные правила. Ошибки разделяются на неверные данные, отсутствие прав, конфликт версии, временную недоступность. Повтор одинаковой операции возвращает первоначальный результат, а изменённое содержимое под тем же ключом отклоняется.

| Канал | Данные | Архитектурная граница |
|---|---|---|
| Мобильное приложение инженера | Собственные задания, диагностика, фото, факт | Служебная аутентификация, права инженера, версия/идемпотентность; офлайн-конфликты проектируются отдельно |
| Telegram | Короткое уведомление о назначении/эскалации | Подписка пользователя и разрешённые идентификаторы; сообщение не меняет состояние без защищённой команды |
| Email | Входящее обращение, уведомление | Message-ID для дедупликации, письмо создаёт черновик до проверки клиента/оборудования |
| Внешняя CRM | Клиенты, контакты, обращения | Таблица соответствия внешняя система+ID↔ссылка; заранее назначается владелец каждого поля |
| Другая база 1С | Номенклатура, акты/платежи при утверждённой схеме | Раздельные контуры управления/учёта, сверка сумм и подтверждений, отсутствие двойного признания |

Предусмотреть будущую очередь исходящих событий: запись вместе с бизнес-транзакцией, отправка после фиксации; повтор с задержкой и журналом, затем ручное решение. Входящие команды — журнал обработанных ключей. Эти очереди описаны как расширение, в первый релиз не включаются. Таймаут интеграции не откатывает завершённое обслуживание. Секреты хранятся отдельно от бизнес-документов и логов.

## Будущий AI-модуль

Граница: бизнес-сервис → обезличенная проекция обращения/истории → адаптер AI → структурированное предложение → проверка → подтверждение человеком. Возможные результаты: тип заявки, приоритет с объяснением, причина, краткое описание, список кандидатов. Ответ содержит версию модели/правил, уверенность, перечень использованных данных и идентификатор запроса.

AI не проводит документ, не назначает инженера, не меняет SLA и не получает весь клиентский справочник. Кандидаты всё равно проходят обязательные фильтры BP-02; некорректная ссылка/тип отклоняется. При таймауте пользователь продолжает стандартный сценарий. Порог доверия, провайдер, допустимые данные и хранение запросов — Q-18. Никаких вызовов AI на текущем этапе.

Официальные страницы платформы проверены 08.10.2026. Они подтверждают существование механизмов, а не предложенные бизнес-правила, схемы регистров или производительность.
