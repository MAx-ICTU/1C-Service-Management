# 17. GitHub, история этапов и передача контекста

## Текущее состояние

Локальный репозиторий инициализирован в outputs, ветка main. Первым коммитом 1ec44b0 сохранена v0.1 до переработки. GitHub remote пока отсутствует; пользовательский URL/параметры нового репозитория запрошены. Нельзя сообщать «отправлено на GitHub» до успешного push/создания коммита на GitHub и проверки ссылки.

Git доступен локально, gh в PATH не обнаружен. Альтернативы после выбора репозитория: обычный Git с установленной аутентификацией либо доступный GitHub-коннектор. Пароли/PAT не запрашиваются текстом чата и не сохраняются в документах; аутентификация штатным способом.

Предпочтительная структура: README.md, docs/, src/config/, tests/protocols/. Локальные базы ib/, backups/, logs/, work/, .env, .cf/.dt/.zip игнорируются. Модули/метаданные штатной выгрузки идут в Git, данные клиентов/пользователей ИБ — нет.

## Фиксация каждого этапа

1. Документация/задача с ID, границами/проверками/неопределённостями.
2. Ветка stage/NN-name от main; один этап может иметь несколько исправляющих коммитов.
3. Diff и протокол с platform/version, commit, действиями/результатами.
4. Push в выбранный origin, PR с описанием/ограничениями.
5. Приёмка/merge, неизменяемый тег завершённого этапа.
6. Обновление 12 и ссылки на commit/PR/tag; отложенные тесты не помечать пройденными.

Для документации текущего этапа допустим отдельный тег docs-v0.2-review: он означает версию на ревью, не утверждение. В существующий непустой GitHub-репозиторий не выполнять force-push и не перезаписывать историю: сначала читать default branch/состав, переносить материалы через отдельную ветку и PR. Для нового пустого репозитория отправить сохранённую последовательность v0.1→v0.2 после выбора владельца/имени/видимости.

## Шаблон протокола этапа

Этап; статус (запланирован/в работе/локально/опубликован/принят); входное разрешение; версия платформы; объекты; действия; результаты/доказательства; невыполненные проверки; дефекты; commit/PR/tag; автор/дата приёмки.

Автор текущих технических коммитов Codex <codex@local.invalid> выбран явно при отсутствии пользовательской Git-идентичности. Будущие коммиты могут использовать согласованные имя/email пользователя без переписывания прошлых.

## Передача в новый чат

К каждому финальному ответу добавляется строка состояния контекста. Точный процент/лимит занятого контекстного окна средствами текущей сессии не доступен; не выдавать подсчитанные символы или лимиты аккаунта за процент контекста. Можно сообщить «точный процент недоступен» и предложить переход при длинной истории.

Начальный пакет нового чата:
- Проект: учебная 1С: Управление сервисной компанией; путь репозитория outputs текущего проекта либо GitHub URL.
- Среда: 8.5.1.1150 учебная, Windows, файловая ИБ, один сеанс, Конфигуратор, без EDT.
- Читать docs/README.md, 05/06/13/15/16, git log/status и 12.
- Текущее состояние: документы v0.2 на ревью, код/объекты/ИБ отсутствуют; команды подтверждены локальной справкой, практический round-trip не выполнен.
- Подтверждения пользователя переносить дословно; отсутствие утверждения не считать разрешением.
- Ближайший шаг: согласовать вопросы/первое задание, затем только bootstrap, без бизнес-кода.
- GitHub: указать выбранный URL/ветку/commit и что уже опубликовано; если remote не задан, написать это явно.
- В конце каждого ответа строка контекста; фиксировать все этапы в Git/GitHub.

Документы являются устойчивой памятью проекта; новый чат не должен восстанавливать бизнес-правила из догадок.
